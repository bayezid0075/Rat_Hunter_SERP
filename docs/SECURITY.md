# Security

## Trust Boundaries

```text
Untrusted client
  -> API key authentication, rate limit, quota, input validation
  -> URL syntax + DNS + address validation
  -> SSRF-safe HTTP fetch and manually validated redirects
  -> HTML extraction (untrusted content)
  -> PostgreSQL / Redis

Untrusted external websites and search pages
  -> bounded HTTP/browser fetchers
  -> parsers that only extract values; no code execution
```

The API is intended to be placed behind a TLS-terminating reverse proxy when accessed beyond localhost. The repository does not provision domains, TLS certificates, or a production reverse proxy.

## Authentication

- Keys are generated by `scripts/create_api_key.py`.
- Raw keys are returned once and never stored.
- Storage uses HMAC-SHA256 with `API_KEY_PEPPER`; only the hash and display prefix are persisted.
- Accepted headers: `X-API-Key` or `Authorization: Bearer ...`.
- Authentication snapshots are cached for `API_KEY_CACHE_TTL` (and may be served from the stale window during a cache backend failure).
- Revocation, account/application disabling, and expiry are enforced from the cached snapshot, so changes can take up to the cache lifetime to take effect. Revoke and then wait at least `API_KEY_CACHE_TTL * 2` when immediate lockout is required, or flush the auth cache.
- Revoked keys, disabled accounts, and disabled applications return `403`; invalid/expired keys return `401`.

Rotate keys by creating a replacement, deploying it to clients, and revoking the old key. Changing `API_KEY_PEPPER` invalidates every stored key hash; plan rotation accordingly.

## Secrets

Required production changes:

- `SECRET_KEY`: replace the development default.
- `API_KEY_PEPPER`: replace the development default and keep it stable for the lifetime of stored keys.
- PostgreSQL and Redis credentials: replace defaults.
- `SENTRY_DSN`: only set if Sentry is intended.
- `.env`: never commit. The provided `.gitignore` excludes it.

Do not put secrets in request payloads, logs, search queries, or documentation. The access log records route, status, duration, and request ID, not API keys or full bodies.

## SSRF Protection

Outbound extraction URL handling rejects:

- non-HTTP/HTTPS schemes
- empty, overlong, or malformed URLs
- URL credentials (`user:password@host`)
- invalid ports
- ports outside `HTTP_ALLOWED_PORTS` (default `80,443`)
- hostnames that fail DNS resolution
- private, loopback, link-local, multicast, reserved, and unspecified addresses
- metadata-service addresses such as `169.254.169.254`
- redirects to blocked targets
- too many redirects

The fetcher disables environment proxy trust (`trust_env=False`), follows redirects manually, revalidates each target, clears cookies after requests, and enforces `HTTP_MAX_RESPONSE_BYTES`.

`SSRF_ALLOW_PRIVATE` defaults to `false`. Do not enable it on an internet-facing deployment. If a trusted internal service requires private addresses, isolate that capability in a separate deployment and network policy.

### DNS Rebinding Caveat

The application resolves and validates addresses before connecting, but DNS can change between resolution and connection. For high-assurance deployments, enforce egress policy at the network layer (for example, deny private ranges from the API/worker network namespace) in addition to application checks.

## Request and Response Limits

- Maximum request body: `MAX_REQUEST_BODY_BYTES` (default 1,000,000 bytes).
- Maximum outbound response: `HTTP_MAX_RESPONSE_BYTES` (default 5,000,000 bytes).
- Maximum redirects: `HTTP_MAX_REDIRECTS`.
- Extraction URL length: 2,048 characters.
- Batch extraction: 1-20 URLs.
- Search query: 1-512 characters.
- Search limit: 1-100; page: 1-10.
- Domain filters: 20 each.
- Main text truncation: `EXTRACTION_MAX_TEXT_CHARS`.
- Request deadlines: quick/deep/global settings plus adapter/extraction timeouts.

## Rate Limits and Quotas

- Per-key sliding-window rate limits use Redis when configured.
- Daily quotas count usage rows since UTC midnight.
- Key-level overrides take precedence over account overrides and defaults.
- Memory rate limiting is process-local and intended only for tests or single-process development.
- Exceeded limits return `429` with details or a structured `rate_limit_exceeded` / `quota_exceeded` error.

Use Redis in any multi-process deployment; otherwise each process maintains an independent limit.

## CORS and Hosts

- `CORS_ORIGINS` defaults to empty. Set an explicit allow-list.
- `ALLOWED_HOSTS` defaults to `*`. Production deployments should set explicit hostnames so `TrustedHostMiddleware` rejects unexpected Host headers.
- Credentials are not enabled in CORS.
- Allowed methods are `GET`, `POST`, and `OPTIONS`.
- Allowed headers are `Authorization`, `Content-Type`, `X-API-Key`, and `X-Request-ID`.

## Browser Security

- Playwright Chromium runs inside the dedicated browser worker process.
- Browser navigation is bounded by timeouts and the browser pool capacity.
- The service does not bypass CAPTCHA, login walls, paywalls, or access restrictions.
- Browser workers should run under a dedicated non-root service account with bounded memory. On Linux, ensure Chromium has adequate shared memory or keep `--disable-dev-shm-usage` enabled.

## Logging and Observability

- JSON logs include request ID, method, path, status, and duration.
- Account ID is attached in context after successful authentication.
- Raw API keys, secrets, and request bodies are not logged.
- Upstream page content should not be logged wholesale.
- Sentry is optional. Configure sampling and data-scrubbing appropriate to your organization before enabling it.
- Prometheus metrics avoid secrets and high-cardinality raw URLs by using route templates and bounded labels.

## Host Hardening

No deployment files are included. Run the API and workers as native supervised services.

Production recommendations:

- run each service under a dedicated non-root operating-system account
- use a process supervisor with restart-on-failure and graceful shutdown
- restrict filesystem permissions so only the service account can read `.env`
- restrict egress to required destinations
- isolate PostgreSQL, Redis, API, and worker networks
- store secrets in a secret manager rather than `.env` where possible
- back up PostgreSQL and test restores
- set Redis authentication/TLS or keep it on an isolated network
- keep Chromium and Python dependencies patched
- terminate TLS outside this project if the API is shared beyond localhost

## Dependency and Static Checks

Run before deployment:

```bash
python -m pip install -e ".[dev]"
python -m ruff check .
python -m ruff format --check .
python -m mypy app
python -m pytest -q
```

The test suite includes SSRF, redirect, private-address, authentication, payload, and validation coverage. It does not prove a live third-party site will remain accessible or safe.

## Vulnerability Reporting

Do not open a public issue containing a working exploit or secret. Provide a minimal reproduction and impact assessment to the repository maintainer through the private channel used by your deployment.

## Explicit Non-Goals

The project does not implement:

- CAPTCHA solving or bypass
- paywall or login bypass
- credential stuffing or account takeover
- stealth evasion of site access controls
- arbitrary code execution from fetched HTML
- JavaScript execution outside the controlled Playwright browser
